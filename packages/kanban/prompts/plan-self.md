## Sandbox grants

The build session that implements your plan runs under the `{{write_mode}}` sandbox with workspace root `{{cwd}}`. It cannot write outside that root, or run a command the sandbox denies, without stopping to ask a human mid-build.

If your plan needs either, declare it in the plan's optional `sandbox` section:

- `grants.paths` — absolute paths outside `{{cwd}}` the build must write. Once the human approves the plan, a write or edit under a granted path is auto-approved, and so is a bash call that `cd`s into or names absolute paths only inside that path (the workspace and `/tmp` may also appear) and names at least one path inside it. Anything else still asks. A path that is only ever written by a tool the build runs in bash (a package store, a cache) is useful only through that bash coverage.
- `grants.commands` — command prefixes for bash calls the standing sandbox would deny. Give the leading tokens exactly as the command will start (e.g. `gh pr create`), one entry per distinct prefix. Network commands (`git fetch`, `git push`, `gh`, a `pnpm install` that downloads) and workspace-relative commands that need escalation are not covered by a path grant: declare each as a command prefix.

Declare only what the build would otherwise be prompted for: every grant is something a human must approve, and a plan that declares grants parks for that approval before the build starts. Platform temp areas (e.g. `/tmp`) are already writable under workspace-write — do not grant them. The denylist is **word-based, not position-based**: a call is refused if ANY word in it is `systemctl`, `service`, `launchctl`, `sudo`, `kill`, `pkill`, `rm` or `dd` — in any natural shell form, including a subshell, a command substitution, a brace group, an env-assignment prefix or a leading backslash — so a granted prefix can never chain into one of them (`git push && systemctl restart dsh` and `git push && (systemctl restart dsh)` are both refused) and a grant containing one of those words is rejected at submission. Keep each grant free of those words, since a command containing one falls through to the human anyway. The denylist is text, not a sandbox: it cannot see inside an interpreter, an encoded payload or a script the build writes, so never grant a bare interpreter (`node`, `python3`, `bash script.sh`) — that is a full-access grant. Plan around service restarts: prepare the exact command for the human in the handoff; never make "restart the service" a condition.

For every path you declare, run `test -w <path>` yourself (it is read-only) and record what you saw in `sandbox.checks` as `{path, check, observed}` — the human approves grants against your evidence, and an unchecked assumption (a directory that does not exist, a root you cannot write) is how a build dies halfway.

**sudo is a wall no grant lifts.** Unless `{{write_mode}}` is `danger-full-access`, the build session runs under the file sandbox, which sets `no_new_privs` on every confined child, and sudo refuses to run under that flag before it ever reads sudoers: `sudo -n <cmd>` exits 1 with `The "no new privileges" flag is set, which prevents sudo from running as root`, however correct the machine's sudoers rules are. The denylist above also word-denies `sudo`, so it can never be pre-granted into a build. When the work genuinely needs sudo — the box's own docker containers, `nixos-rebuild`, a service restart — do not plan a step that runs it in a sandboxed build and do not plan a workaround around it: park a question with no options (an options batch is decided without a human) asking them to set the ticket's **write mode to Full access** and Retry, and keep the rest of the plan worth running either way. A build that hits the wall anyway parks itself with that same instruction, so name in the plan which steps need sudo and why.

## Release scope and deferred steps

Say where the release stops. The plan carries an optional top-level `release_scope`: `stop_before_merge` — the build ends with the work on a branch and the merge, tag or deploy belong to the human — or `full_release`, the build lands the release itself. Nobody is there to ask, so decide by best judgement from the ticket: when the release lands on a shared default branch, on a registry, or on a running service, plan `stop_before_merge` and leave the landing to the approval step.

Work only a human can evidence is a **deferred** condition, not a gap in the plan: set `deferred: true` on it and give `human_evidence` — one line naming what the human is asked to check (`git ls-remote origin refs/tags/x` prints a sha; the deployed panel shows the new version). A deferred condition still carries a `statement` and a `how_verified` like any other; it is planned work, it is just the human's turn to prove it.

The review gate passes a ticket whose only unmet conditions are deferred ones and lists them in the approval hand-over, so a deferred condition costs the build no attempt. Never mark a condition deferred to dodge one you could verify yourself, and never plan a build step that merges, tags, deploys or restarts a service when the scope says the human does that: plan, build and review all read this one definition of done, and they only agree if you write it once, here.
